# OpenFlux

OpenFlux — экспериментальный TCP-туннель. Текущий MVP поднимает локальный SOCKS5-прокси, передаёт каждый SOCKS5 `CONNECT` через аутентифицированное WSS/TLS-соединение на контролируемый exit node и открывает с него обычное исходящее TCP-соединение.

Цель этого этапа — небольшой и проверяемый транспорт, а не красивое приложение.

## Поддерживаемый путь MVP

```text
Приложение
  -> SOCKS5 на 127.0.0.1:1080
  -> отдельное WSS-соединение с аутентификацией для каждого SOCKS CONNECT
  -> OpenFlux exit на контролируемом VPS
  -> обычное исходящее TCP-соединение
```

Реализовано и проверено тестами:

- SOCKS5 `CONNECT` без аутентификации;
- только TCP-потоки;
- IPv4-адреса и доменные имена;
- DNS-разрешение на exit node;
- проверка TLS-сертификата, включая необязательный частный CA;
- аутентификация bearer-токеном и WebSocket-подпротокол `openflux.v1`;
- необязательный HTTP- или SOCKS5-прокси для начального WSS-подключения;
- корректное закрытие слушателей и активных туннелей;
- проверка политики назначения до исходящего соединения с VPS.

Текущие ограничения:

- нет UDP и SOCKS5 `BIND`;
- нет IPv6-назначений;
- нет мультиплексирования: для каждого SOCKS-соединения создаётся отдельное WSS-соединение;
- TUN не входит в поддерживаемый WSS-маршрут;
- нет входящего проброса портов;
- выбирается только первый включённый маршрут;
- инструкции по systemd пока отсутствуют намеренно.

> Работающий WSS-туннель **не доказывает** работу через белые списки российских операторов. Поведение зависит от оператора, тарифа, региона и конечного адреса и должно проверяться отдельно с официально разрешённым транспортом. V2rayN можно использовать как контролируемый начальный путь, но успех через него не подтверждает самостоятельную доступность OpenFlux.

## Сборка

Используйте версию Go из [`go.mod`](go.mod):

```bash
go build -o openflux .
```

Корневой модуль использует локальный вложенный модуль [`fluxcore`](fluxcore/), поэтому собирать нужно из корня репозитория.

## Конфигурация

OpenFlux загружает JSON через `--config`, раскрывает переменные окружения, проверяет всю конфигурацию и запускает первый включённый маршрут.

В репозитории есть два безопасных шаблона:

- [`flux.example.json`](flux.example.json) — клиент с SOCKS5 только на localhost;
- [`flux.exit.example.json`](flux.exit.example.json) — exit node, который для первого теста слушает только localhost VPS и доступен через SSH port-forward.

Скопируйте их в локальные неотслеживаемые файлы:

```bash
cp flux.example.json flux.client.json
```

```bash
cp flux.exit.example.json flux.exit.json
```

Вместо токена в примере указана переменная окружения:

```json
"authToken": "${OPENFLUX_AUTH_TOKEN}"
```

Передайте клиенту и exit node **один и тот же** случайный токен. Он должен содержать не менее 32 символов без пробелов; подходят 32 случайных байта, закодированные 64 шестнадцатеричными символами. Не храните токен в Git, чате, снимках экрана, аргументах процесса и логах. Если `OPENFLUX_AUTH_TOKEN` не задан, проверка конфигурации завершится ошибкой — запуск без аутентификации невозможен.

### TLS-файлы

Exit node требует:

- `certFile` — серверный сертификат, при необходимости вместе с цепочкой;
- `keyFile` — соответствующий закрытый ключ, доступный только сервисной учётной записи exit node.

В Subject Alternative Name сертификата должно присутствовать имя, используемое при проверке. Клиент использует системное хранилище доверия либо CA из `caFile`. Необязательный `serverName` переопределяет только проверяемое TLS-имя и не отключает проверку сертификата.

Относительные пути `caFile`, `certFile` и `keyFile` разрешаются относительно JSON-файла конфигурации.

Небезопасного режима пропуска проверки сертификата намеренно нет.

## Первый foreground-тест

Этот сценарий оставляет WSS-порт закрытым извне и не требует изменений firewall, маршрутов, NAT, DNS, raw sockets или systemd.

### 1. Подготовьте exit node

Поместите конфигурацию exit node и TLS-сертификат/ключ на VPS. Сохраните безопасную привязку из примера:

```json
"listenAddr": "127.0.0.1:8443"
```

Замените документационный адрес в `denyCIDRs` на публичный IPv4-адрес VPS с маской `/32`. Exit node и так запрещает адреса своих локальных интерфейсов, но явный `/32` фиксирует ожидаемую границу.

Задайте `OPENFLUX_AUTH_TOKEN` через защищённый механизм окружения и запустите процесс в foreground:

```bash
./openflux --config flux.exit.json
```

В ожидаемом выводе есть выбранный маршрут `wss` и строка `WSS exit listening on 127.0.0.1:8443`. Токен и содержимое закрытого ключа не должны появляться в выводе.

### 2. Создайте локальный SSH port-forward

Через уже авторизованное SSH-подключение к VPS перенаправьте локальный порт клиента на слушатель exit node:

```bash
ssh -N -L 18443:127.0.0.1:8443 user@your-vps
```

Если SSH сейчас работает через V2rayN, сохраните эту уже проверенную схему SSH. В MobaXterm эквивалентом будет local port forward с `127.0.0.1:18443` на `127.0.0.1:8443` со стороны VPS.

### 3. Подготовьте и запустите клиент

Клиентский шаблон подключается к локальному SSH-forward:

```json
"endpoint": "wss://127.0.0.1:18443/openflux/v1/tunnel"
```

Укажите в `serverName` точное DNS-имя из SAN сертификата exit node и задайте `caFile`, если используется частный CA. Передайте тот же `OPENFLUX_AUTH_TOKEN`, затем запустите:

```bash
./openflux --config flux.client.json
```

Ожидаемая строка запуска:

```text
SOCKS5 listening on 127.0.0.1:1080
```

### 4. Отправьте контролируемый трафик

Используйте удалённый DNS через SOCKS (`--socks5-hostname`, а не `--socks5`) и контролируемый HTTP-адрес:

```bash
curl --socks5-hostname 127.0.0.1:1080 https://your-controlled-test-host.example/
```

Проверьте:

- контролируемый ответ приходит без искажений;
- имя назначения разрешается на VPS, а не на клиенте;
- внешний адрес источника совпадает с адресом VPS;
- loopback, private, link-local, локальные адреса VPS и настроенные запрещённые сети недоступны;
- параллельные запросы работают;
- Ctrl+C корректно закрывает слушатели и активные потоки;
- в логах нет токена, заголовка Authorization, учётных данных прокси, cookie, закрытого ключа и полезной нагрузки.

Не добавляйте systemd и не открывайте публичный WSS-порт, пока foreground-тест не станет понятным и воспроизводимым.

## Необязательный начальный прокси для WSS

Для контролируемой проверки WSS-адреса, уже доступного снаружи VPS, добавьте в клиентский маршрут:

```json
"proxyURL": "socks5://127.0.0.1:10808"
```

Поддерживаются `http` и `socks5`. Для SOCKS5 нужно явно указать порт. Нельзя направлять `proxyURL` на собственный SOCKS-порт OpenFlux (`127.0.0.1:1080`) — получится цикл. Не помещайте учётные данные прокси в отслеживаемую Git конфигурацию.

## Политика адресов exit node

Перед соединением exit node:

1. строго разбирает `host:port`;
2. один раз выполняет IPv4 DNS-разрешение на VPS;
3. проверяет каждый полученный адрес;
4. соединяется только с уже проверенными литеральными IPv4-адресами.

Политика отклоняет IPv6, unspecified, loopback, private, link-local, multicast, CGNAT, benchmark, documentation, reserved, адреса локальных интерфейсов и сети из `denyCIDRs`. Если запрещён хотя бы один DNS-ответ, запрос отклоняется. Это исключает DNS rebinding между проверкой и соединением.

## Проверка при разработке

Сначала отдельно запустите тесты вложенного модуля конфигурации, затем корневой набор:

```bash
go -C fluxcore test ./...
```

```bash
go test ./...
```

Статический анализ и локальная сборка:

```bash
go vet ./...
```

```bash
go build ./...
```

Статическую сборку для Linux/amd64 можно создать так:

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o build/openflux-linux-amd64 .
```

Автоматические тесты используют локальные слушатели и подменённые resolver/dialer; для них не нужны MAX, Yandex, публичный интернет или VPS.

## Экспериментальные старые пути

Yandex Docs, Yandex Volga, OneMe/MAX, CupsOnline, пакетный транспорт, gVisor и raw exit mode оставлены в репозитории для исследовательской совместимости. Они **не** входят в поддерживаемый MVP и могут требовать учётных данных, повышенных привилегий или сетевого поведения, которого WSS-дизайн намеренно избегает.

Текущие [`Dockerfile`](Dockerfile), [`docker-compose.yml`](docker-compose.yml), [`.env.example`](.env.example) и `docker/entrypoint.sh` всё ещё описывают старый контейнерный путь. Не используйте их как инструкции по развёртыванию WSS. Для первой проверки WSS предназначен foreground-сценарий выше.
