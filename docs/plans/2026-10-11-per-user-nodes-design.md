# Персональная нода на каждого подписчика (дизайн)

Дата: 2026-10-11.
Статус: согласован.

## Проблема

Сейчас выходная нода общая: пул `main` → канал `fork-all`, один key/порт/
комнаты на всех подписчиков. Один юзер создаёт нагрузку и риски для всех;
нет изоляции ни по ключу, ни по транспортам. Требуется: у каждого подписчика
своя нода (свой канал, ключ, порт, комнаты) и, в перспективе, свои документы
всех перевозчиков.

## Цель

1. Каждый подписчик получает **личный канал** `u<hex>` на пуле с `perUser`.
2. Личный канал создаётся **лениво** — по первому запросу подписки, тем же
   механизмом single-flight + cooldown, что и авто-нода пула.
3. Транспорты личного канала — из шаблона пула: `cupsonline` (свои комнаты) и
   `direct` (свой порт) создаются автоматически сегодня.
4. Документы `vyandex/mailru/boards` — через слот `DocFactory` на служебных
   аккаунтах (этап 2, когда аккаунты есть). Сейчас слот реализован, но без
   аккаунтов документы не создаются.
5. Общие пулы (`of-rpc7n5`) остаются общими и служат запасным путём.
6. Подписчик не видит `null`: пока канал создаётся — `profiles: []`.

## Модель и конфигурация

Пул получает признак `perUser`:

```json
{ "id": "main", "name": "Основной", "perUser": true, "mode": "l4",
  "transports": [ { "type": "cupsonline" }, { "type": "direct" } ] }
```

- У `perUser`-пула нет фиксированного `channel`. Имя канала выводится из юзера:
  `u` + первые 18 символов hex от sha256(userID), например
  `u1a2b3c4d5e6f708090`. Имя удовлетворяет правилу `node-install.sh`
  (`^[a-z0-9][a-z0-9-]{0,30}$`).
- Детерминированное имя — источник истины вместо мапы юзер→канал: идемпотентно,
  ключ single-flight = имя канала, при рестарте сервис просто видит готовый
  `node.conf`.
- `transports` у `perUser`-пула — шаблон:
  - `cupsonline` с пустым `url` → свои комнаты на юзера;
  - `direct` → свой порт (номер выбирает `node-install.sh`);
  - `vyandex`/`mailru`/`boards` → заполняет фабрика (этап 2); пока аккаунта нет,
    транспорт просто не попадает в канал (в логе видно).
- Не-`perUser` пулы не меняются.
- `Config.Check()`: для `perUser`-пула `channel` не требуется; проверяется
  корректность шаблона транспортов и `mode`.

## Провиджининг и выдача

- `nodeProvisioner.Ensure` принимает запрос `{Pool, Channel, User}` (нужны
  конкретное имя канала и юзер для фабрики).
- `profiles()` для `perUser`-пула вычисляет канал юзера; если `node.conf` есть —
  отдаёт его профиль; если нет — запускает создание (single-flight + cooldown по
  имени канала) и пока отдаёт `profiles: []`.
- Первый запрос подписки лениво создаёт личный канал — один systemd-юнит
  `openflux-node@u<hex>` на юзера.
- Дефолтный (первый по приоритету) профиль у юзера — личный.

## DocFactory (слот под документы)

```go
type DocFactory interface {
    // Make создаёт юзеру документ у перевозчика и возвращает ссылку + cookies,
    // которыми нода его читает.
    Make(ctx context.Context, carrier, user string) (url, cookies string, err error)
}
```

- Конфиг: секция `docAccounts` — по одной сессии (cookie-jar) на перевозчика;
  пусто = фабрики нет.
- Cookies кладёт оператор один раз после ручного логина (SmartCaptcha Yandex
  проходим руками), не автоматический вход логин/пароль.
- Этап 1 (сейчас, аккаунтов нет): `Make` для `vyandex/mailru/boards` возвращает
  «не настроено»; канал юзера создаётся с cups+direct.
- Этап 2 (когда аккаунты есть): фабрика отдаёт `url`+`cookies`, провижионер
  кладёт их в личный канал (`vyandex=`/`cookies=` — механизм `node-install.sh`
  уже есть, `transport/yandex` читает cookie-jar).

## Жизненный цикл

- Создание: лениво при первом запросе подписки.
- Удаление/бан/истечение: **не удаляем** (YAGNI). Каналы переживают истечение;
  сборщик «мёртвых» каналов — возможный этап 3. При `DELETE /api/v1/account`
  канал пока остаётся.

## Ошибки и наблюдаемость

- `profiles: []` (никогда `null`) пока канал в процессе/упал.
- Лог: `pool main: user <id>: channel u<hex>: autoNode: <plan|apply>: <error>`.
- Если личный канал не поднялся — юзер всё равно получает общие
  `of-rpc7n5`-профили.
- `/admin/info` показывает пул и число личных каналов, чтобы `opensub status`
  был осмысленным.

## Тесты

- per-user: первый запрос создаёт канал `u<hex>`, второй — нет; ключ
  single-flight = имя канала.
- два юзера → два разных канала; канал одного не виден другому.
- готовый канал юзера → профиль отдаётся, `Ensure` не зовётся.
- фабрика без аккаунта → канал без документов, общий l3 на месте; фабрика с
  фейком → документ попал в канал и профиль.
- не-`perUser` пул по-прежнему общий (регресс).
- `profiles` не бывает `null` во всех ветках.

## Миграция

- В config `main`: `perUser: true`, `transports: [cupsonline, direct]`, поле
  `channel` убираем/игнорируем.
- Старый общий `fork-all` остаётся работать; новых/существующих юзеров он не
  касается. Позже можно снести вручную (`node-install.sh remove fork-all`).
- Выпуск: пересборка linux-бинарника, бэкап config, рестарт, проверка:
  `opensub status` ok, у тестового юзера появился `u<hex>` и профиль `main` —
  его личный.
